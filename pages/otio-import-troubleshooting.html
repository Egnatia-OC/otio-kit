otio-kit · import notes

Your OTIO file imports wrong into Resolve. Six causes, and the check that confirms each.

These are the failures I hit importing generated OTIO into Resolve Free 21.1.0.0017 on Ubuntu 24.04 and Windows 10, in the order they waste the most time. Every one is reproduced and written up in the fidelity log. Resolve's importer reports almost none of them: several fail silently, which is why they cost hours.

Scope: the causes below are established on Free 21.1 on the two platforms listed. Studio and other builds may behave differently. If you test one, the report template takes ten minutes and gets your build number into the registry.

1. The timeline imports empty, with no error at all

Symptom: a timeline appears with zero clips. No dialog, nothing in the import log, no clue.

Cause: the file contains a custom OTIO schema Resolve does not know — for example an effect named AudioFadeIn_1 instead of the stock Effect.1. Unknown schemas are treated as fatal. When it does surface, the message is the unhelpful Import Log (Fatal) - failed to import OTIO timeline.

Check: find every OTIO_SCHEMA in the file and confirm it is stock. Custom schemas usually come from a tool exporting its own effect objects.

grep -o '"OTIO_SCHEMA": *"[^"]*"' timeline.otio | sort -u

Anything not in the OpenTimelineIO schema set is your failure. The same file will also fail OpenTimelineIO's own deserializer, so a five-line Python check confirms it before you blame Resolve.

2. Every clip lands offline, or you get a relink dialog per clip

Symptom: clips import but show as media offline, or a chain of "clips not yet found" dialogs.

Cause: relative media URLs. On Linux the conform step misresolves them. It is filename/reel based, not just path based, so the file being on disk is not enough.

Fix: write absolute paths to media that exists at import time. If the timeline has to move between machines, rewrite the media references on the target machine before importing rather than relying on relative paths.

3. The clip imports, but there is no picture — audio only

Symptom: the timeline is there, the audio plays (or meters move), the video is black.

Cause: H.264/H.265 on Resolve Free on Linux. Those decoders are Studio-only on that platform. The container's AAC track parses, so the clip imports as audio-only and looks like a timeline bug.

Fix: transcode to DNxHR (SQ or HQ) before importing. The same clips import with full picture on Windows and macOS Free — this is a platform-scoped gap, not a file-format problem. If your file imported fine on Windows and looks broken on Linux, this is why.

4. The music bed is silent

Symptom: the audio clip is present and placed correctly, but nothing is audible.

Cause: AAC. Free Linux cannot decode it, so an music.m4a-style bed imports as a silent clip. No error is raised.

Fix: ship PCM/WAV-class audio for Linux targets. A WAV bed and AAC bed of the same content can look identical in the file and behave differently on the timeline.

5. A marker is missing

Symptom: you emitted two markers, one imported.

Cause: markers are clip-local in OTIO as Resolve imports it. A marker whose time falls outside the clip it is attached to is dropped, with no message.

Fix: attach each marker to the clip that actually spans its time, and keep marker times inside that clip's range. This is the same on Linux and Windows, so it is an emitter rule, not a platform quirk.

6. The audio fade-in is not applied

Symptom: the clip imports with no fade handle and a flat waveform.

Cause: a custom fade schema is either ignored or fatal (see cause 1). The representation that is recognized is the stock Effect.1 schema with effect_name: AudioFadeIn and the duration in parameters as a RationalTime.

Status: verified applied on Free 21.1 on Windows (clip handle present, waveform ramping over the first two seconds). Unverified on Linux — the test machine has no audio path, so nothing there can confirm an applied fade. Do not read "it imported" as "it was applied".

Two smaller ones worth knowing

SymptomCause
Total duration is a few frames offDurations are quantized per clip to whole frames. At 23.976 or 29.97 fps the sum drifts by a few frames over a minute. This is the model, not corruption.
EDL imports but timing is rejected"Failed to link … timecode extents do not match" means the pool has different media than the EDL describes. Also: CMX_3600 cannot carry a dissolve, stills and markers in one file — that is why OTIO is the primary format.

Before you file it as a Resolve bug

Do these four checks in order. They separate emitter bugs from importer limits, and they are exactly what a useful report contains:

  1. List the distinct OTIO_SCHEMA values. Stock only?
  2. Are all media paths absolute and existing at import time?
  3. Is the platform Free-Linux, and is the footage H.264 or AAC?
  4. Do the markers sit inside the clip durations they are attached to?

If all four pass and it still fails, that is a real finding — and the fidelity report template is the fastest way to get it into the record with the build number attached.
